# Zend X Chain — Arquitectura

L1 propia, escrita desde cero (sin adoptar un framework de chain tipo Cosmos SDK/Substrate), pensada para ser construida por un equipo chico en ~12 meses sin sacrificar seguridad de forma imprudente. Reemplaza el enfoque documentado anteriormente en `zendx/src/components/token/TokenSpecsCard.jsx` (ZNX como BEP-20/ERC-20 sobre una chain existente) — esos componentes de la web quedan desactualizados hasta que se actualicen en una tarea aparte.

## Decisiones de arquitectura

**Lenguaje: Rust** (edition 2021, runtime `tokio`). Memory-safety en compile-time es crítico para código que maneja llaves privadas y fondos reales. Se apoya en crates maduros y activamente mantenidos (`libp2p`, `ed25519-dalek`, `rocksdb`, `borsh`) en vez de reinventar primitivas criptográficas/de red.

**Consenso: Prueba de Trabajo (PoW) abierta** — pivote decidido el 2026-07-21, reemplaza el diseño anterior de validador fijo (round-robin) + gadget de finalidad BFT (nunca se implementó). Decisión de negocio explícita: la chain pasa a ser permissionless (cualquiera puede minar, sin que Zend X controle quién produce bloques), a costa de finalidad determinística — ver `CONSENSUS.md` para el diseño completo (emisión con halving, reajuste de dificultad, fork-choice).

**Estado: UTXO**, no cuentas — cambia junto con el consenso: sin validator set permisionado, no tiene sentido seguir modelando "una cuenta, un balance" al estilo Ethereum; el modelo de salidas no gastadas es el que corresponde a una chain abierta estilo Bitcoin. Esto significa que las transacciones ya no tienen `from`/`to`/`nonce` — gastan salidas previas (`OutPoint`) y crean salidas nuevas (`TxOut`, pay-to-pubkey-hash simplificado, sin lenguaje de script).

**Sin VM en año 1**: sigue sin haber bytecode interpretado — la única lógica de estado es la transición UTXO (`znx-state`) más las reglas de consenso de PoW (`znx-consensus`). El módulo `governance` (alta/baja de validadores) del diseño PoA anterior ya no aplica — no hay validator set que gobernar. Toda la lógica de negocio de producto (tiers XP, cashback, etc.) se queda off-chain en la plataforma. Una VM (WASM tipo CosmWasm, o EVM-compatible) sigue como decisión consciente de v2.

**Networking: `libp2p`** — TCP + Noise (cifrado) + Yamux. Sin Kademlia DHT (lista estática de bootnodes pasada por CLI). `gossipsub` para tx/bloques. Es transporte puro, agnóstico del mecanismo de consenso — el pivote de PoA a PoW no le exigió ningún cambio. El `request-response` para votos de consenso del diseño anterior ya no aplica (no hay votos que juntar sin gadget de finalidad).

**Unidades**: montos en `u128`, 18 decimales (misma convención que la mayoría de tokens EVM) — ver `genesis/devnet.json`.

## Estructura del workspace

```
blockchain/
├── Cargo.toml                 # workspace root
├── genesis/devnet.json        # parámetros de emisión (subsidio+halving) y dificultad inicial, chain-id
├── docs/ARCHITECTURE.md, CONSENSUS.md
└── crates/
    ├── znx-crypto/      # firmas ed25519, hashing blake3, address, bech32 (prefijo znx1...)
    ├── znx-types/       # Address, OutPoint, TxOut, TxIn, Transaction, Block, BlockHeader (UTXO + campos PoW)
    ├── znx-codec/       # serialización canónica (borsh), merkle root, hash-vs-target de PoW
    ├── znx-storage/     # RocksDB: UTXO set, bloques, undo data (para reorg de 1 bloque)
    ├── znx-state/       # state transition function UTXO: apply_transaction/apply_coinbase, OverlayStore
    ├── znx-mempool/     # pool de txs pendientes: valida firma/chain_id/outpoints, rechaza doble gasto en el pool
    ├── znx-consensus/   # verificación de PoW, reajuste de dificultad, calendario de halving, trabajo/target
    ├── znx-p2p/         # swarm libp2p: gossipsub (tx/bloques) + request-response (pedido punto a punto) + allow_block_list/connection_limits (baneo de peers) — transporte puro, agnóstico del consenso
    ├── znx-rpc/         # API JSON-RPC completa (jsonrpsee): submit_transaction, list_unspent, get_latest_height, get_block(_by_hash), get_transaction, get_mempool_info, get_mining_info — vía el trait RpcNode, que znx-node implementa
    ├── znx-node/        # nodo: minero PoW abierto + validación estricta + reorg de 1 bloque + RPC mínimo
    ├── znx-wallet/      # keystore cifrado + selección de UTXOs + armado/firma/envío de una transferencia — compartido por znx-wallet-cli y znx-custody
    ├── znx-wallet-cli/  # CLI: keygen, address, balance (suma de UTXOs), send — capa delgada encima de znx-wallet
    ├── znx-custody/     # servicio de firma de retiros para el backend de zendx (ver docs/INTEGRATION.md): sign_withdrawal/custody_address vía RPC, sin exponer la llave privada fuera del proceso
    └── znx-testkit/     # harness de devnet multi-nodo: orquesta el binario real de znx-node como subproceso (TestNode::spawn/wait_for_height/balance)
```

Todos los crates del workspace están implementados y testeados (82 tests unitarios + 3 tests de integración real marcados `#[ignore]`: 2 en `znx-testkit` que levantan 2 nodos reales y confirman que convergen a la misma altura/vía IBD, y 1 en `znx-custody` que confirma un retiro firmado moviendo fondos reales de punta a punta — correr con `cargo test -p <crate> -- --ignored`). `znx-testkit` reemplaza el proceso manual (bash + `curl` + `nohup`) que se usó para cada verificación en vivo de esta sesión por una API reusable (`TestNode::spawn`, `wait_for_height`, `balance`, `write_test_genesis` con dificultad ajustable).

## Pivote de 2026-07-21: PoA+cuentas → PoW abierta+UTXO

Decisión de negocio explícita (no técnica): la chain deja de ser un libro mayor permisionado que Zend X controla, y pasa a ser una red abierta estilo Bitcoin — cualquiera puede minar, el supply se emite por minería con halving en vez de pre-mintearse. Esto reemplaza, no extiende, el diseño de Fase 2 planeado (BFT + round-robin desaparecen del roadmap; PoW + fork-choice por hash de header los reemplaza — ver `CONSENSUS.md`). Contexto legal importante: tener blockchain propia (PoW o no) **no reemplaza** el trabajo de licenciamiento/regulatorio de la plataforma (VASP/PSAV, AML) — son pistas paralelas, no una precondición de la otra.

Lo implementado en esta misma sesión y verificado (65 tests unitarios + un devnet real de 2 nodos a mano): tipos UTXO + campos de PoW en el header (`znx-types`/`znx-codec`, con merkle root real reemplazando el hash-concatenado-plano anterior), transición de estado UTXO con `OverlayStore` para validar-antes-de-comprometer (`znx-state`), UTXO set + undo data en RocksDB (`znx-storage`), mempool por outpoints reclamados en vez de nonces (`znx-mempool`), reglas de consenso PoW — verificación, reajuste de dificultad, calendario de halving (`znx-consensus`, repropósito del crate que iba a tener el gadget BFT), loop de minería + validación estricta + reorg de hasta `MAX_BACKFILL_DEPTH` (20) bloques de profundidad (`znx-node`), y selección de UTXOs en la wallet CLI. `znx-p2p` sumó `request-response` (protocolo `/znx/block-sync/1`) para el pedido punto a punto de bloques que el backfill necesita — el resto de la propagación (gossipsub) no cambió.

**Deliberadamente fuera de alcance** (documentado, no descubierto después): forks de más de `MAX_BACKFILL_DEPTH` bloques de profundidad (equivalente a lo que en cadenas reales resuelven los checkpoints/weak subjectivity), un protocolo de descarga por lotes de verdad para IBD (hoy pipeline de pedidos individuales en paralelo, más simple que un mensaje "dame el rango N..N+K" pero con más round-trips), elegir la mejor cadena entre varios peers a la vez (IBD sincroniza contra un peer por vez), priorización de mempool por fee-rate (FIFO simple alcanza para hoy). Los parámetros de `genesis/devnet.json` siguen siendo solo de devnet — los de mainnet ya están decididos por separado (`docs/CONSENSUS.md`, "Parámetros de mainnet"), no son los mismos valores.

## Roadmap (revisado 2026-07-21 — dedicación full-time, después del pivote a PoW)

**Nota de dedicación**: a partir de acá Zend X Chain es foco full-time (no en paralelo con el resto de la plataforma `zendx`). El roadmap original de 12 meses era optimista en un punto concreto que NO se comprime agregando más horas de un solo dev: una auditoría externa (Fase 5) depende del calendario de una firma de terceros — agendarla, esperar el resultado, corregir hallazgos, posible re-auditoría — no del esfuerzo interno disponible. (El otro punto de fricción original, el testing adversarial de un gadget BFT, ya no aplica — PoW no tiene ese componente.)

Total revisado: **~15-16 meses desde el arranque de la dedicación full-time** (vs. 12 originales). Se re-revisa esta estimación al cerrar cada fase, no es un compromiso fijo. El pivote a PoW no necesariamente acorta el total — cambia DÓNDE está el trabajo (menos testing adversarial de BFT, pero más hardening de red abierta: resistencia a mineros maliciosos, forks más profundos, eclipse attacks sobre gossipsub).

- **Fase 0** (semanas 1-3): workspace + CI + `znx-crypto`/`znx-types`/`znx-codec`. **Completada.**
- **Fase 1** (implementación inicial completada, endurecimiento pendiente): `znx-storage`, `znx-state`, `znx-mempool`, `znx-node`, `znx-wallet-cli` — hoy ya en su versión UTXO+PoW (ver pivote arriba), verificados end-to-end. Keystore de `znx-wallet-cli` ya cifrado (Argon2id + XChaCha20-Poly1305, ver `crates/znx-wallet-cli/src/keystore.rs`) — cerró el pendiente de "llave privada en 32 bytes crudos sin cifrar". Falta antes de cerrar la fase: una ronda de dogfooding/hardening más larga (no solo el smoke test de hoy).
- **Fase 2** (implementación inicial completada tras el pivote, endurecimiento parcial): `znx-p2p` (gossipsub + request-response, `allow_block_list` + `connection_limits`), `znx-consensus` (PoW: verificación, reajuste de dificultad, halving — ya no BFT), reorg de hasta 20 bloques de profundidad + sincronización completa (IBD) para distancias mayores, tope de mempool, puntaje de mala conducta por peer con baneo automático, loop principal no bloqueante (ver "Endurecido contra peers maliciosos" abajo), `znx-testkit` (harness de devnet multi-nodo, ver más abajo). Resistencia a eclipse attacks — mitigación parcial (2026-07-21, ver el comentario de módulo de `znx-p2p`): tope de conexiones por vecindario de red (`MAX_CONNECTIONS_PER_NETGROUP`, agrupado /16 IPv4 / /32 IPv6) contra un atacante concentrado en un rango de IPs, más rotación periódica de la conexión saliente más vieja con re-dial a los bootnodes (`OUTBOUND_ROTATION_INTERVAL`) — sigue sin haber descubrimiento de peers, así que un nodo cuyos bootnodes configurados estén TODOS comprometidos desde el arranque no queda cubierto por esto. Peer scoring de gossipsub (2026-07-21): validación manual (`validate_messages`) + `with_peer_score` — reputación continua por peer/tópico (P1 tiempo en el mesh, P2 primeras entregas, P4 mensajes inválidos, P6 colocación por IP), P3 desactivado a propósito para nuestros dos tópicos de baja frecuencia (ver comentario de `topic_score_params` en `znx-p2p`); complementa, no reemplaza, el ban list explícito por strikes. `target_block_time_secs`/`difficulty_adjustment_interval_blocks` de mainnet ya decididos (ver `docs/CONSENSUS.md`, "Parámetros de mainnet") — solo falta benchmarkear `initial_target` con hardware representativo antes del lanzamiento real.

### Endurecido contra peers maliciosos (2026-07-21)

Revisando el código de esta misma fase se encontró un bug de impacto real, no solo "falta hardening": `run_main_loop` (`znx-node`) procesaba cada mensaje entrante `.await`-eado **en serie** — un peer que mandara un bloque huérfano disparando `backfill_and_reorg` (hasta 20 round-trips de red con timeout) dejaba al nodo entero sin procesar NINGÚN otro mensaje mientras tanto. Se corrigió spawneando cada `handle_inbound` en su propia tarea — verificado en vivo bajo carga real (2 nodos con géneros de dificultad distintos generando cientos de intentos de backfill fallidos entre sí) que el RPC sigue respondiendo de inmediato durante todo ese proceso.

Además: tope de `MAX_MEMPOOL_SIZE` (10.000 tx pendientes, rechaza en vez de desalojar — sin priorización por fee-rate, desalojar abriría una vía de "sacar la tx de otro sin costo"), y un puntaje de mala conducta simple por peer (`SharedNode::strikes`, contador en memoria sin persistencia): un bloque gossipeado o una respuesta de backfill que no valida suma un strike, y al llegar a 5 se banea al peer vía `znx_p2p::NetworkHandle::ban_peer` (behaviours oficiales `allow_block_list` + `connection_limits` de `libp2p`, no lógica casera). El camino de baneo se ejercita indirectamente por los tests existentes de `try_reorg_to_chain` (que cubren exactamente la condición de error que dispara un strike) — no se demostró un baneo real de punta a punta en esta sesión (el intento con 2 nodos de géneros distintos divergió tanto desde el bloque 0 que el backfill nunca llegó a completarse y ejecutar la validación real, quedó como prueba de la corrección de responsividad en cambio).
- **Fase 3** (implementación inicial completada): `znx-rpc` completo — reemplazó el stopgap embebido en `znx-node` (trait `RpcNode` + `submit_transaction`/`list_unspent`/`get_latest_height`/`get_block`/`get_block_by_hash`/`get_mempool_info`/`get_mining_info`/`get_transaction`). `get_transaction(txid)` (2026-07-21) agrega un índice txid→altura nuevo en `znx-storage` (`CF_TX_INDEX`, poblado en `commit_block` y limpiado en `undo_latest_block`, así un reorg lo deshace igual que el resto del estado) — ya cerrado. Integración con el backend de `zendx` (2026-07-21, ver `docs/INTEGRATION.md`): `znx-custody` (servicio de firma de retiros) implementado y verificado end-to-end. La lógica de keystore cifrado + selección de UTXOs + armado/firma/envío de una transferencia, antes duplicada dentro del binario de `znx-wallet-cli`, se extrajo a un crate compartido nuevo (`znx-wallet`) — `znx-wallet-cli` pasó a ser una capa delgada de CLI encima de eso. `znx-custody` reusa `znx-wallet` para exponer un único método JSON-RPC de escritura (`sign_withdrawal`) protegido por un token compartido comparado en tiempo constante (fail-closed si no está configurado) — nunca maneja bytes de clave privada fuera de su propio proceso, y no está pensado para exponerse a internet (bind a localhost/red privada). Pendiente antes de cerrar la fase: decidir el mecanismo de auth final (mTLS/red privada) y cablear la Edge Function real de `zendx` contra este servicio — ambos documentados en `INTEGRATION.md`. (El módulo `governance` del diseño PoA anterior ya no aplica — no hay validator set que gobernar.)
- **Fase 4** (≈2.5-3 meses): testnet 24/7 en infraestructura real, métricas/tracing, chaos testing, fuzzing de parser de tx y deserialización de red — tiempo de calendario real corriendo la red, no comprimible con más horas.
- **Fase 5** (≈3-5 meses): auditoría externa (firma especializada en consensus/blockchain — agendar con 4-8 semanas de anticipación, más la duración de la auditoría, más remediación de hallazgos). Calendario de emisión (incluido el premine, ver abajo) y tiempos de bloque/reajuste de mainnet ya decididos (`docs/CONSENSUS.md`); falta rehacer el benchmark de `initial_target` con hardware representativo (el de hoy es una estimación de un solo dato de sandbox, no un valor final), generar y asegurar en frío las direcciones reales de premine (fuera de alcance del código — es un proceso de custodia de claves, no se generaron direcciones reales en esta sesión), y armar el `genesis/mainnet.json` real.

**Seguridad continua desde Fase 0**: `cargo-audit` en CI (`.github/workflows/blockchain-ci.yml`), `clippy` estricto (deny por defecto vía `[workspace.lints]`), fuzzing de rutas críticas desde que existen, revisión de seguridad dedicada por crate crítico (`znx-consensus`, `znx-crypto`, `znx-state`) antes de dar cada uno por cerrado.

`blockchain/.cargo/audit.toml` ignora 2 RUSTSEC de `hickory-proto` (2026-07-21) — llegan al `Cargo.lock` vía `libp2p-dns`/`libp2p-mdns`, pero `znx-p2p` fija `libp2p` sin las features `dns`/`mdns` (ver arriba), así que ese código nunca se compila (verificado con `cargo tree -i hickory-proto`, que no encuentra nada) — no es un riesgo real de esta chain, es ruido del lockfile de un crate paraguas. Revisar ese ignore si alguna vez se activa descubrimiento de peers por mDNS o direcciones `/dnsN/...`.
